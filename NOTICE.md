# Provenance

The content of the [`compile/`](compile/) folder is extracted from
[`packages/php-wasm/compile`](https://github.com/WordPress/wordpress-playground/tree/trunk/packages/php-wasm/compile)
of the [WordPress Playground](https://github.com/WordPress/wordpress-playground)
project (via our fork
[php-kirigami/php-wasm-builder](https://github.com/php-kirigami/php-wasm-builder)),
under the GPL-2.0-or-later license (see [`LICENSE`](LICENSE)).

What was extracted (see `CLAUDE.md` for details):

- `compile/base-image/`, `compile/php/`, `compile/Makefile`,
  `compile/build.js`, and the per-library Docker recipes (`compile/lib*/`,
  `compile/oniguruma/`).
- Prebuilt binaries (`*/dist/`) were **not** copied: they are rebuilt via
  `make`/Docker instead of being vendored, to stay consistent with the goal
  of being able to update PHP/extensions/libs easily (see
  `../kirigami/todo.md`).
- Playground's optional shared extensions (`intl`, `xdebug`, `redis`,
  `memcached`, under `compile/shared/` upstream) were not ported for
  now — out of scope for the MVP.
- `libncurses`/`libedit` exist upstream but are disabled (commented out) in
  their own `Makefile` — not carried over here.

`compile/libwebp/Dockerfile` was fixed relative to upstream Playground
(2026-09-11), two separate bugs:

1. Added `--host wasm32-unknown-emscripten` to the `emconfigure ./configure`
   call. Without it, the `configure` regenerated by `autoreconf`/`autoconf`
   (unlike other libs that use an already-generated `configure`) doesn't
   determine that it's cross-compiling and crashes with
   `cannot run C compiled programs` when trying to run a WASM binary
   natively.
2. Build/install `sharpyuv` and `src` directly (`make -C sharpyuv`,
   `make -C src`) instead of the top-level recursive `make`/`make install`,
   which also descends into `imageio`/`examples`/`man`/`extras`. Building
   the `examples` CLI tools (cwebp/dwebp/etc.) failed under `wasm-ld` with
   `duplicate symbol` errors, because `libwebp.a` ends up listed twice on
   the link line (once via an absolute-ish path, once via a relative one)
   and `wasm-ld`'s `--whole-archive` linking rejects that, unlike a
   traditional linker. We only need `libwebp.a`/`libsharpyuv.a` (and the
   nested `src/demux`, `src/mux` archives), not the CLI tools. (A
   command-line `SUBDIRS=` override on the top-level `make` was tried
   first, but that value propagates into every nested Makefile too,
   breaking `src/Makefile`'s own, unrelated `SUBDIRS` list.)

`compile/libxml2/Dockerfile` and `compile/oniguruma/Dockerfile` were
fixed the same way, preemptively (2026-09-11), before actually hitting the
failure: both regenerate `configure` via `autogen.sh`/`autoreconf` like
`libwebp` did, and were missing `--build`/`--host`/`--target`, so the same
`cannot run C compiled programs` crash would have hit them too. Every other
lib Dockerfile under `compile/lib*` ships an already-generated `configure`
and doesn't regenerate it, so this class of bug is now believed to be fully
addressed (checked by grepping for `autoreconf`/`autogen`/`autoconf` across
every lib Dockerfile).

`compile/libssh2/` and `compile/nghttp2/` are new (2026-09-12), not part of
the original Playground extraction — added for curl SFTP/SCP and HTTP/2
support respectively. Adding `libssh2` surfaced a real, previously-unnoticed
bug affecting the whole build: `libz`'s and `libopenssl`'s `make install`
produce both static (`.a`) and shared (`.so*`) artifacts side by side, and
`wasm-ld` refuses a generic `-L`/`-l` search that happens to resolve to the
`.so` ("attempted static link of dynamic object") — every other lib
Dockerfile avoided this by referencing the `.a` file by exact path, but
`libssh2`'s autoconf-generated dependency check doesn't. Fixed generally via
`compile/Makefile`'s `STRIP_SO` macro, called right after `libz`/`libopenssl`
populate their dist directories (the only two libs consumed as a build-time
dependency by other lib Dockerfiles).

`compile/libcurl/Dockerfile`'s pinned curl version was bumped from 7.69.1 to
8.22.0 (2026-09-12, matrix.json's "always try latest first" default policy —
see `CLAUDE.md` decision 26). curl 8.x added a hard dependency on `libpsl`
(Public Suffix List, used for cookie-domain-matching security) that we don't
vendor; fixed by adding `--without-libpsl` to the `configure` flags — this
just disables that one optional hardening feature, curl otherwise builds and
works identically (HTTP/2 via `nghttp2` confirmed still enabled in the build
log).

The `Dockerfile` under `compile/php/` contains patches added by the user on
top of upstream Playground (originally flagged via French comments in the
file, since translated): stripping opcache JIT sources incompatible with
WASM, native compilation of `minilua`/`gen_ir_fold_hash`, and a Makefile fix
for PHP 8.5.
